Expert Parallelism, in 300 Lines of NumPy

Three hundred lines of NumPy and mpi4py. Two MPI primitives. One verification harness. The whole MoE training pattern, with nowhere to hide.
by Ved · systems engineer at Axolotl AI
github / ved1beta · x / @ant_vedaya

A year ago I wrote my first MoE in CUDA. This post is about writing my second one — in NumPy, sharded across processes with mpi4py. About three hundred lines, two MPI primitives doing the heavy lifting, one verification harness that proves the sharded gradients match the single-process reference to machine epsilon.

This is a sequel to GPU-sanghathan, which already had data parallelism and pipeline parallelism wired through mpi4py — the same MPI Python bindings used for HPC and research codebases for years. I wanted to see what changed when expert parallelism (EP) joined the stack. The answer turned out to be: a lot, and the interesting parts are at the seams.

· · ·

§ 01Why expert parallelism exists

Modern frontier models — GPT-4, DeepSeek-V3, Mixtral — are all mixtures of experts. The motivation: at fixed compute per token, can we cram in more parameters? Yes, and the trick is sparsity.

Inside each transformer block, instead of one FFN that processes every token, you have N FFNs (“experts”) and a small router. The router is a Linear(d_model, n_experts) followed by softmax. For each token, you pick the top-k experts (typically k=2) and run only those. Their outputs are gate-weighted and summed.

A 64-expert MoE with top-k=2 has roughly 32× the parameters of a single FFN, but each token only touches 2 of 64. Same flops per token, far more capacity. The router is trained jointly with the experts via a load-balancing auxiliary loss — without it, the router collapses to “always pick expert 0” and 63 of your experts go cold.

The four parallelism axes

Modern training stacks compose four orthogonal ways of splitting work across GPUs. This project implements three; tensor parallelism is the fourth.

  • Data parallel (DP). Each GPU has a full copy of the model. Each processes a different slice of the batch. After backward, every GPU’s gradients are averaged via Allreduce. The cheapest axis — DistributedDataParallel in PyTorch.
  • Tensor parallel (TP). Splits individual weight matrices across GPUs. A Linear(4096→4096) becomes “GPU 0 owns half the columns, GPU 1 owns the other half.” Each does half the matmul, then they Allreduce. Used when single matrices stop fitting in one GPU’s memory.
  • Pipeline parallel (PP). Splits the model between layers, like an assembly line. GPU 0 owns layers 1–8, GPU 1 owns 9–16; activations Send/Recv between adjacent stages.
  • Expert parallel (EP). Different experts live on different GPUs. The router stays replicated, but tokens are shipped via Alltoall to the rank that owns their chosen expert, run there, then shipped back. The new comm primitive — Alltoall — is what makes EP qualitatively different from DP and PP.

All four compose. A typical large-scale MoE run might use DP=64 × PP=8 × EP=8 across 4096 GPUs.

§ 02Wiring the process grid

Before anything else, organise the workers. Three axes, every rank getting its own coordinate (dp_idx, pp_idx, ep_idx). Rank 0 is at the corner, rank 1 sits one step over on the EP axis, and so on:

rank = dp_idx · (PP·EP)  +  pp_idx · EP  +  ep_idx

Why count EP first? Because EP is the chattiest axis — it fires an alltoall every time an MoE layer runs forward — so we want EP-adjacent ranks to land on the same socket if we can help it. Rank 0 and rank 1 should be next-door neighbours, not on opposite sides of a cluster.

For each axis we need a sub-communicator: a slice of the world containing exactly the ranks that should talk to each other for that one purpose. MPI hands us Split(color, key) — same color means same group — and the rest is bookkeeping.

def make_comms(DP, PP, EP, world=None):
    if world is None:
        world = MPI.COMM_WORLD
    rank   = world.Get_rank()
    ep_idx = rank % EP
    pp_idx = (rank // EP) % PP
    dp_idx = rank // (EP * PP)

    ep_comm = world.Split(color=dp_idx * PP + pp_idx, key=ep_idx)
    pp_comm = world.Split(color=dp_idx * EP + ep_idx, key=pp_idx)
    dp_comm = world.Split(color=pp_idx * EP + ep_idx, key=dp_idx)
    return dp_comm, pp_comm, ep_comm, (dp_idx, pp_idx, ep_idx)

The trick is in the colors. Each one fixes two of the three coordinates and lets the third vary. dp_comm groups ranks that share (pp, ep) — model replicas that should average gradients. pp_comm groups ranks that share (dp, ep) — pipeline stages that hand off activations. ep_comm groups ranks that share (dp, pp) — expert peers that all-to-all tokens.

Spin this up at world=8, DP=PP=EP=2 and you get four EP groups, four PP groups, four DP groups, each containing exactly two ranks. Twenty lines and the entire process grid is wired.

§ 03A drop-in MoE, single-process first

The MoE layer presents itself like a Linear. From outside it’s just another module you stick into a Sequential:

layers = [
    Linear(784, 128, activation="relu"),
    MoE(in_dims=128, hidden_dims=64, out_dims=128,
        n_experts=4, top_k=2, ep_comm=ep_comm),
    Linear(128, 10, activation=None),
    Softmax(),
    CrossEntropyLoss(batch_size=GLOBAL_BATCH_SIZE),
]

Inside it builds two things. A router — a small Linear(in_dims, n_experts) that scores how much each token wants each expert. And the experts themselves — copies of a 2-layer FFN, one per local expert. The “local” matters: if ep_comm=None or has size 1, this rank holds all the experts. If EP > 1, it holds only n_experts / ep_size of them.

There’s a subtle bit that took some debugging. NumPy’s Linear seeds itself deterministically from (in_dims, out_dims) only — same shape, same init — great for reproducibility but disastrous for MoE: every expert would be born identical, and the router would have no signal to discriminate. Fix: re-seed each expert from its global id, not its local index.

self.experts = [Sequential([
    Linear(in_dims, hidden_dims, activation="relu"),
    Linear(hidden_dims, out_dims, activation=None),
]) for _ in range(self.n_local_experts)]

for local_e, expert in enumerate(self.experts):
    global_e = local_e * self.ep_size + self.ep_rank
    self._reinit_expert(expert, global_e)

This is the small invariant that lets the EP-sharded run produce the same expert weights as a single-process run — expert 7 has the same weights whether it’s the only expert on a rank, or one of sixteen on a single machine. We’ll lean on that later when we test for correctness.

The constructor also tags every MoE-owned parameter with _skip_ep_allreduce = True when EP > 1. We’ll come back to why a few sections from now — right now it’s a sticker the gradient sync code reads later.

The single-process forward

The cleanest way to learn the EP path is to first see what it’s mimicking. Without EP — single process, all experts on one rank — the entire MoE forward is three phases.

Route. Run the router, softmax it, pick the top-k experts per token, and renormalise their gates so they sum to one:

gates = softmax(self.router(inputs))                    # (T, E)
top_k_idx = np.argsort(-gates, axis=-1, kind="stable")[:, :k]
top_k_gates_raw = gates[np.arange(T)[:, None], top_k_idx]
top_k_gates = top_k_gates_raw / top_k_gates_raw.sum(axis=-1, keepdims=True)

top_k_idx[t, j] is “the j-th best expert for token t.” Renormalising the chosen gates turns the gated combine at the end into an honest convex combination, which keeps the activations from drifting weirdly.

The kind="stable" is there for EP. With a stable sort, every rank breaks ties identically, so when several ranks see the same input they all reach the same routing decision. Without it, two ranks could disagree about which expert a borderline token wants — and then send it to two different places. Silent corruption. The stable sort costs nothing and rules that out.

Dispatch. Walk over each expert, find the tokens routed to it, run them through, scatter the gated results back:

out = np.zeros((T, out_dims), dtype=np.float32)
for e in range(E):
    tok_idx, slot_idx = np.where(top_k_idx == e)
    if tok_idx.size > capacity:
        tok_idx, slot_idx = tok_idx[:capacity], slot_idx[:capacity]
    expert_out = self.experts[e](inputs[tok_idx])
    w = top_k_gates[tok_idx, slot_idx][:, None]
    np.add.at(out, tok_idx, expert_out * w)

np.where(top_k_idx == e) returns paired arrays of (token row, slot column) for every place expert e shows up in the top-k matrix. Capacity caps how many of those an expert is allowed to process — overflow drops silently to zero in out. And np.add.at is the unbuffered scatter-add, because the same token row can show up multiple times (once per expert it routed to) and ordinary out[tok_idx] += ... doesn’t accumulate duplicates correctly.

Auxiliary loss. Without help, the router collapses to “always pick expert 0” within a couple hundred steps. The fix is a tiny gradient signal that pushes routing toward uniformity:

counts = np.array([d[0].size for d in dispatch], dtype=np.float32)
f = counts / max(n_assigned, 1)
P = gates.mean(axis=0)
aux_loss = self.aux_loss_coef * E * float((f * P).sum())

fe is the fraction of routed slots that went to expert e. Pe is the mean gate probability for expert e. Multiply, sum across experts, and you get a quantity minimised at perfect balance (f = P = 1/E). The clever bit is that f is treated as a constant (it’s a count, not differentiable), so all the gradient flows through P — which is exactly the lever we’d want to pull to nudge things toward balance.

That’s the whole single-process MoE. Forty lines, three phases. Now we make it talk over the network.

§ 04Sharding the experts across ranks

Here’s where EP earns its name. Instead of one rank holding all the experts, every rank holds a slice — n_experts / R each. The router stays replicated on every rank (because every rank needs to make its own routing decisions for its own tokens), but the experts are spread out.

That means a token on rank 0 might want an expert that lives on rank 3. So we have to ship it. The single-process for e in range(E) loop becomes a six-step communication protocol:

[locally]
  1. Run router; pick top-k experts per token.
  2. For each (token, slot), figure out which rank owns the chosen expert.
  3. Bucket tokens by destination rank.

[over the network]
  4. Alltoallv: every rank ships its bucketed tokens to their destinations.

[locally on the receiving rank]
  5. Group received tokens by local expert; apply capacity; run.

[over the network]
  6. Reverse Alltoallv: ship raw expert outputs back to where they came from.

[locally on the origin]
  7. Combine: weight by gate, scatter-add into the output.

In code:

T_global = self.ep_comm.allreduce(T, op=MPI.SUM)
capacity = int(np.ceil(self.capacity_factor * T_global * k / E))

# routing — same as single-process
gates = softmax(self.router(inputs))
top_k_idx = np.argsort(-gates, axis=-1, kind="stable")[:, :k]
# ... renormalize ...

# bucket by destination rank
dest_rank = top_k_idx % R
send_tokens, send_local_eid, origin_idx = [], [], []
for dr in range(R):
    mask = (dest_rank == dr)
    t_idx, slot_idx = np.where(mask)
    local_eid = (top_k_idx[t_idx, slot_idx] // R).astype(np.int32)
    send_tokens.append(inputs[t_idx])
    send_local_eid.append(local_eid)
    origin_idx.append(np.stack([t_idx, slot_idx], axis=-1))

# ship the tokens (and a bit of metadata)
recv_tokens    = alltoallv_v(self.ep_comm, send_tokens,    np.float32)
recv_local_eid = alltoallv_v(self.ep_comm, send_local_eid, np.int32)
all_tokens    = np.concatenate(recv_tokens, axis=0)
all_local_eid = np.concatenate(recv_local_eid, axis=0)
sources = np.concatenate([np.full(t.shape[0], s) for s, t in enumerate(recv_tokens)])

# run experts that live on this rank
out_per_recv = np.zeros((all_tokens.shape[0], out_dims), dtype=np.float32)
for local_e in range(self.n_local_experts):
    sel = np.where(all_local_eid == local_e)[0]
    if sel.size > capacity:
        sel = sel[:capacity]
    out_per_recv[sel] = self.experts[local_e](all_tokens[sel])

# ship the outputs back
send_back = [out_per_recv[sources == s] for s in range(R)]
recv_back = alltoallv_v(self.ep_comm, send_back, np.float32)

# combine on origin
out = np.zeros((T, out_dims), dtype=np.float32)
for dr in range(R):
    oi = origin_idx[dr]
    if oi.shape[0] == 0: continue
    t_idx, slot_idx = oi[:, 0], oi[:, 1]
    w = top_k_gates[t_idx, slot_idx][:, None]
    np.add.at(out, t_idx, recv_back[dr] * w)

Three pieces of bookkeeping carry the whole thing. origin_idx[dr] remembers, for each destination rank, which local (token, slot) pairs we shipped to it — these never travel over the wire, they’re our breadcrumbs for putting results back where they belong. sources records, for each row of all_tokens we received, which rank originally sent it — used in step 6 to slice the outputs correctly per destination. And local_eid = global_eid // R translates between the global expert space (0..E-1) and the local one (0..E/R-1) the receiving rank actually has.

Capacity is computed against T_global, not the local T. That’s a one-int Allreduce per forward and it’s the difference between EP-and-single-process dropping the same tokens vs. dropping different tokens. It also costs nothing.

Per MoE forward, then: three Alltoallvs and one Allreduce-of-an-int. That’s the full network bill.

Variable-size all-to-all, in two parts

Alltoallv is the variable-size all-to-all primitive — every pair of ranks can exchange a different number of elements. mpi4py exposes it as a C-flavoured call you have to feed packed buffers, per-destination counts, and offsets. Manageable, but fiddly. The alltoallv_v helper hides the packing:

def alltoallv_v(comm, send_chunks, dtype=np.float32):
    R = comm.Get_size()
    # ... infer trailing shape, build sendcounts, pack sendbuf ...

    recvcounts = np.empty(R, dtype=np.int32)
    comm.Alltoall(sendcounts, recvcounts)        # ← pass 1: counts
    rdispls = np.zeros(R, dtype=np.int32)
    rdispls[1:] = np.cumsum(recvcounts[:-1])
    recvbuf = np.empty(int(recvcounts.sum()), dtype=dtype)

    comm.Alltoallv(                               # ← pass 2: payload
        [sendbuf, sendcounts, sdispls, MPI.FLOAT],
        [recvbuf, recvcounts, rdispls, MPI.FLOAT],
    )
    # ... unpack into per-source list of arrays ...
    return recv_chunks

The interesting thing is that this is two MPI calls, not one. The receiving ranks don’t know how much is coming until they’re told — somebody has to tell them — so we do a small fixed-size Alltoall of just the byte counts, then the actual variable-size Alltoallv of the payload. Two collectives where you might expect one.

These two collectives have very different cost profiles. The counts exchange is small and latency-bound: a handful of ints, dominated by the round-trip time. The payload exchange is bandwidth-bound: many megabytes of token activations, dominated by network throughput. When you start optimising EP, this distinction matters — the latency-bound piece is what you want to fold into compute via async, the bandwidth-bound piece is what wants bigger chunks.

The same dance, in reverse

Backward mirrors forward almost exactly. Two more Alltoallvs in the opposite directions. The renormalize–softmax–router chain stays purely local on origin. And there’s one extra collective at the end that forward doesn’t have.

The whole thing in order:

  1. Origin: compute the gate gradient locally (it has expert_outs cached from forward).
  2. Origin: prepare d_expert_out = dout · gate, queue it per destination.
  3. Alltoallv: ship d_expert_out to where the expert lives.
  4. Receiver: run expert.backward() on the routed slice.
  5. Alltoallv (reverse): ship d_input back to where the tokens came from.
  6. Origin: scatter d_input into the right rows.
  7. Origin: backprop through renormalize → softmax → router (purely local).
  8. Allreduce router grads across ep_comm.

The gate gradient in step 1 falls out of differentiating out[t] = Σ_j gate[t,j] · expert_out[t,j] with respect to gate[t,j]. It’s an inner product over the output dimension:

d_top_k_gates[t_idx, slot_idx] += (d_out_e * ob).sum(axis=-1)

d_out_e is dout[t_idx], ob is the cached recv_back[dr] from forward — the wire-roundtripped expert outputs. We need them on the origin side because that’s where the router lives, that’s where the gate gradient ultimately gets used.

Step 8 is the one piece backward has that forward doesn’t:

for p in self.router.parameters():
    if p.requires_grad:
        self.ep_comm.Allreduce(MPI.IN_PLACE, p.grad, op=MPI.SUM)

The router is replicated across ep_comm peers — every rank has identical router weights. Each rank computed the gradient from its own slice of tokens; summing those slices across EP reconstructs the full global gradient. SUM, not mean. Each rank’s gradient is already its share, scaled correctly because the loss divides by the global batch size up front. Summing gives the right answer; dividing afterwards would give the average, which is wrong by a factor of ep_size.

This is the bug that did exist in an early version of this codebase, undetected for a while because the equivalence test only asserted “all peers agree” — and Allreduce makes that true regardless of whether you divide or not. Tightening the test to assert “EP gradient equals the single-process reference” caught it instantly. The lesson: in distributed code, “all ranks agree on the wrong answer” is a class of bug that demands a stronger oracle than peer comparison.

§ 05Three reduction rules, one little tag

Now the part that’s actually the most subtle — gradient sync when DP and EP and PP all stack on top of each other.

Different parameter classes need different reductions:

ParameterReplicated acrossHas to sum over
Router (in MoE)DP × EPDP and EP both
Experts (in MoE)DP only — different EP ranks own different expertsDP only
Other dense layers (the surrounding Linears)DP × EPDP and EP both

Three different reductions over three different sub-communicators is messy if you implement it directly. The cleaner thing is to use a single tag, set at construction time:

if self.ep_size > 1:
    for p in self.router.parameters():
        p._skip_ep_allreduce = True
    for expert in self.experts:
        for p in expert.parameters():
            p._skip_ep_allreduce = True

Every MoE-owned parameter — router and experts both — gets stamped. Then the post-grad hook in pipe.py reads it:

def backprop_block_and_ep_allreduce(ep_comm, params):
    # First wait for all the DP allreduces to finish
    MPI.Request.Waitall([p._request for p in params if p._request is not None])

    # Then sweep EP allreduce, but only for params not tagged
    if ep_comm and ep_comm.Get_size() > 1:
        for p in params:
            if not p.requires_grad: continue
            if getattr(p, "_skip_ep_allreduce", False): continue
            ep_comm.Allreduce(MPI.IN_PLACE, p.grad, op=MPI.SUM)

The DP allreduce already happened (asynchronously, overlapped with backward). This hook fires after backward is done. It waits for DP to finish, then walks every parameter and EP-allreduces the ones without the tag.

What each parameter class actually gets:

  • A regular Linear outside the MoE has no tag, so it gets the DP allreduce and the EP allreduce → summed across both axes. ✓
  • An expert’s parameters have the tag, so they get the DP allreduce but no EP allreduce → summed across DP only, which is what we want because different EP ranks have different experts. ✓
  • The router is tagged too, so it gets DP allreduce here. But the router also got an EP allreduce inside _backward_ep (step 8). So the router ends up summed across both axes through two different code paths. ✓

Three lines of tagging, one branch in the hook, no extra communicators. Every parameter ends up correctly synchronised regardless of how the world is sliced.

§ 06What this is, what it isn’t

That’s the whole implementation. About three hundred lines of NumPy and mpi4py, two MPI primitives doing the heavy lifting (Send/Recv for PP, Alltoallv for EP), one parameter tag handling all the gradient-sync distinctions, one verification harness keeping it honest.

It runs on CPU instead of GPU, blocks during the alltoalls instead of overlapping them with compute, and dispatches each expert as a separate NumPy call instead of fusing them into one matmul. Those three things are most of why production EP is fast — and none of them change the algorithm. Bucket, ship, run, ship back, combine, regardless of substrate.

If you want the production version, look at Megatron-LM’s MoE path or DeepSpeed-MoE — both written for GPU and NCCL, both with the overlap and fusion this implementation skips. Once you’ve watched the six-step protocol happen in three hundred lines of NumPy, the production code stops feeling like magic.
