Trained a tiny GPT in JAX, and the framework kept surprising me

A 10M-parameter character-level GPT, six layers deep, trained on TinyShakespeare. The math was familiar; the shape of the code was not.
by Ved · systems engineer at Axolotl AI
github / ved1beta · x / @ant_vedaya

The goal was deliberately small: a transformer tiny enough to read in one sitting, but real enough to train. I wrote a 10M-parameter character-level GPT in JAX with Equinox and Optax, pointed it at TinyShakespeare, and let it run. The architecture was not the surprise. What kept catching me off guard was how functional the framework feels once you stop thinking in modules and start thinking in pure operations over trees of arrays.

The first thing that threw me, coming from PyTorch, was that the model has no batch dimension. I write the forward pass for one sequence and then add the batch from the outside in one line:

logits = jax.vmap(lambda i, k: model(i, k, inference))(x, keys)  # (B, T, vocab)

That feels backwards at first, and then it stops feeling backwards at all. The body of the model reads like the equations because there are no batch axes cluttering it up. And when I want to spread the same code across devices later, the model itself does not change; I swap the mapping transform at the boundary.

The model is just data

An Equinox module is a PyTree whose leaves are the weight arrays, with configuration sitting next to them as plain Python values. Once that clicks, a lot of everyday PyTorch habits stop making sense. Parameter groups are no longer a string-matching chore. I want weight decay on matrices but not on biases or norms, so I ask each leaf whether it is at least rank-2:

wd_mask = lambda m: jax.tree_util.tree_map(lambda p: p.ndim >= 2, m)

That is the same model metadata I would usually chase through named parameters and special cases, except here it is just a predicate over a tree. It is simpler, but also more honest about what the code is doing.

Mixed precision is a cast

My favorite part is mixed precision, because there is no global mode to turn on. I keep the master weights in float32, do the big matmuls in bfloat16, and make the cast explicit inside the function I differentiate:

cmodel = _to_dtype(model, jnp.bfloat16)
logits = jax.vmap(...)(x, keys).astype(jnp.float32)

The important bit is that the gradients still come back in float32 on their own. I do not keep a second copy of the weights around. There is no optimizer-side bookkeeping for precision state. The types and autodiff sort it out between them. And because bfloat16 keeps float32’s exponent range, the loss-scaling dance that usually comes with float16 never shows up.

Attention is one call

Self-attention is equally blunt:

out = jax.nn.dot_product_attention(q, k, v, is_causal=True)

The naive version builds the full score matrix, which scales as the square of sequence length and spends most of its time moving memory around. This call does not build that matrix. On GPU it drops to a single flash-attention kernel, and the causal mask is just a flag instead of a dense tensor full of negative infinities.

That is the recurring pattern in JAX: the framework keeps asking me to express intent, not machinery. I do not describe the implementation path. I describe the operation, and the compiler figures out a much better path than I would have written by hand.

· · ·

Staying on the compiler’s good side

The rest of the training loop is an exercise in respecting the compiler. jit turns the step into one compiled graph, so every trip back into Python costs you. I keep the data on device and grab batches inside the compiled step so nothing gets copied each iteration. Dispatch is async, so I only pull the loss back to the host every so often. Read it every step and you stall the pipeline waiting on the host. The step also donates its buffers, so the updated weights reuse the same memory.

That all sounds like plumbing, but the effect is conceptual as much as it is performance-related. The compiler is not an afterthought here. It is part of the programming model.

How it went

Five thousand steps took about 44 minutes. The loss starts at about ln(65) ≈ 4.17, exactly random guessing over 65 characters, and drops quickly.

Watch the gap. The training and validation losses fall together until about step 3000, then split: training keeps sliding down while validation parks itself around 1.54. That is the model starting to memorize the training text instead of learning anything that transfers. For 10M parameters on roughly a million characters, it is exactly where I would expect it to land.
